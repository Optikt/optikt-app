## Idea
SvelteKit 3.1.0 es stable desde 2026-10-14. La migración no es un bump: cambia el dueño de la configuración (svelte.config.js -> plugin sveltekit() en vite.config.ts), elimina $lib en favor de #lib (2.817 ocurrencias en 719 archivos, 393 specifiers únicos, 38 imports a directorios), elimina $app/stores (ya no se usa), renombra $app/environment -> $app/env y depreca $env/*, cambia $app/paths (resolve sin slash inicial), vuelve readonly page.url, elimina handleValidationError, exige field.as(...) en remote forms (29 form(), 20 componentes con enhance, ~157 name= manuales más nombres dinámicos en prescription/product/lens), y adapter-node 6 elimina ORIGIN. Ya se cumplen Vite 8.3.4, Svelte 5.57.2 y plugin-svelte 7.3.1; faltan Kit 3.1.0, adapter-node 6.0.0, Node >=22.17 y el codemod. TS7 NO entra: Kit 3.1.0 peer typescript ^6.0.0, svelte-check 4.7.7 peer ^5||^6 y typescript-eslint 8.71.2 <6.1.0; se queda TypeScript ~6.0.3 (no ^6.0.3: 6.1 rompe el peer de typescript-eslint). Estrategia: branch propio, un commit por task de `npx sv migrate sveltekit-3`, revisar @migration-task/MIGRATION_TASKS.md, y gates después de cada fase.

## Estrategia de branches

- `main` se queda en SvelteKit 2 y **no recibe ninguna fase**. Solo hotfixes críticos; nada de codemods ni bumps de Kit/adapter-node.
- `migrate/sveltekit-v3` es la rama de integración de larga vida. Sale de `main` y recibe los PRs de cada fase.
- Cada fase sale de `migrate/sveltekit-v3` en una rama corta (`migrate/sk3-f0-baseline`, `migrate/sk3-f1-deps`, `migrate/sk3-f2-config`, etc.) y vuelve a la rama de integración por PR, nunca a `main`.
- El PR principal es `migrate/sveltekit-v3 -> main`. Se puede abrir en draft desde el inicio para ver el diff acumulado, pero **no se mergea** hasta que todas las fases estén verdes y la validación local (con DB duplicada en Supabase) pase.
- Al empezar cada fase, hacer `merge main -> migrate/sveltekit-v3` (no rebase) para absorber hotfixes sin reescribir la historia de la integración. Resolver conflictos en la rama de fase.
- Gates: PR de fase exige `pnpm check` + `pnpm lint` + tests de la fase; la rama de integración exige el set completo; el PR final exige build, unit, integration, e2e, knip y smoke local con `node build` + Supabase duplicada.
- CI: los workflows de `pull_request` escuchan `main`, `develop` y `migrate/**` (los PRs de fase apuntan a `migrate/sveltekit-v3`); `push` corre solo en `main`, `develop` y `migrate/sveltekit-v3` para no duplicar el suite en cada push de fase.
- Rollback: revertir el merge de la fase en `migrate/sveltekit-v3`. `main` queda intacto.
- No hay staging remoto: la integración se ejecuta y valida en local (`pnpm dev` / `node build`) contra una DB duplicada en Supabase. `main` sigue siendo la referencia estable de Kit 2.
- Dependabot sigue bloqueando majors de Kit/adapter-node en `main`; en la integración los bumps se hacen a mano dentro de la fase que corresponda.
- TS7 no se toca en esta rama: cuando Kit/svelte-check/typescript-eslint lo soporten, se abre otra migración desde `main` ya mergeada.

## Decisiones cerradas

- **Entorno (cerrado).** No hay staging remoto. La migración se ejecuta y valida en local contra una DB duplicada en Supabase. Nunca apuntar a la DB de producción.
- **Origin/CSRF (cerrado).** Producción es `https://optikt.taild8f0b9.ts.net` (Dokploy + acceso por Tailnet); el 502 de `nanezx-elitebook...` es un host local sin app y no aplica. No hardcodear `paths.origin`: setear `PROTOCOL_HEADER=x-forwarded-proto` y `HOST_HEADER=x-forwarded-host` en el contenedor; si el header no llega, adapter-node usa `host` y protocolo `https` como fallback. **Verificado 2026-10-23** con `tcpdump` en el puerto interno `3001`: el contenedor recibe `Host: optikt.taild8f0b9.ts.net`, `X-Forwarded-Host: optikt.taild8f0b9.ts.net` y `X-Forwarded-Proto: https` (los agrega Tailscale Serve). Por tanto adapter-node 6 calcula `https://optikt.taild8f0b9.ts.net` correctamente; no hace falta `paths.origin`. Configurar igualmente `PROTOCOL_HEADER=x-forwarded-proto` y `HOST_HEADER=x-forwarded-host` para no depender del fallback. Para `node build` local sobre HTTP, compilar con `PATHS_ORIGIN=http://localhost:3000` o validar con `pnpm dev` (dev no aplica el CSRF de producción).
- **Remote forms (cerrado).** Híbrido: field-backed (`field.as(...)`) para inputs/textarea/select nativos y formularios simples; hidden input `field.as('hidden', value)` como puente solo para third-party (Svelecte, bits-ui Select/Combobox) y formularios complejos que dependen de estado local. Prohibido `name` manual. El puente se acepta como **deuda post-migración**: se documenta y se limpia en una migración posterior a field-backed total; no bloquea este plan.
- **`handleError` (cerrado).** `app` devuelve el body; `framework` conserva status/message; `validation` devuelve `buildValidationMessage(issues)`; `unknown` loguea completo server-side y responde `{ message: 'Internal Error' }` sin `cause`.
- **Env (cerrado).** `DATABASE_URL` requerido; `EXCHANGE_RATES_*`, `PRINT_AGENT_*`, `DOKPLOY_*`, `BACKUP_NOTIFY_TOKEN` y `CHROMIUM_PATH` opcionales con default seguro. PRINT_AGENT no bloquea el arranque.
- **Remote functions (cerrado).** Se mantienen experimentales (`experimental.remoteFunctions` + `compilerOptions.async`); no se migran a load/actions en este plan.
- **Criterio de merge final (cerrado).** QA local completo + 48h de uso local con la DB duplicada (soak = período de observación antes de mergear), sin errores nuevos en logs, y gates completos. No hay preview remoto.
- **Docs (cerrado).** Actualizar docs activos (`AGENTS.md`, `.github/instructions`, `README`, `components.json`); no tocar planes/specs históricos.

## Riesgos y mitigaciones

- **Diff masivo de `$lib` (719 archivos).** El task `lib-alias` resuelve 393 specifiers únicos, 38 directorios a `index.js` y conserva `.svelte`; no hay imports extensionless a `.svelte` (verificado). Aun así, revisar `git diff --stat` y separar en commit propio. Rollback: revertir ese commit.
- **Remote forms es el mayor riesgo funcional.** Kit 3 rechaza `name` manual al submit; no basta con compilar. Migrar por dominio (auth, customers/prescription, brands/materials, suppliers, products, lenses, users/settings) y probar cada flujo con browser/e2e. Para controles third-party usar hidden input con `field.as('hidden', value)` como puente; no dejar `name` manual.
- **`handleError` cambia de contrato.** Antes `handleValidationError` manejaba validación; ahora todo pasa por `handleError` con `kind`. Si se retorna el mensaje crudo para `unknown`, se filtran detalles; si se loguea todo, se ensucia el log con 404/401 esperados. Ramificar por `kind` y responder `{ message: 'Internal Error' }` para `unknown`.
- **`page.url` readonly.** `replaceUrlSearch` y `getUrlKey` reciben `URL`; `ReadonlyURL` no es asignable por `searchParams`. Cambiar firmas a `{ href }` / `{ pathname, search }` antes de que `pnpm check` lo marque.
- **`verbatimModuleSyntax`.** `$app/tsconfig` lo activa; habrá imports de tipo sin `import type` y barrels con `export` en vez de `export type`. Resolver con diagnósticos de `svelte-check`, no con `skipLibCheck`.
- **`ORIGIN` y CSRF en deploy.** adapter-node 6 ignora `ORIGIN`. En Dokploy/Tailscale validar `PROTOCOL_HEADER`/`HOST_HEADER`; si el proxy no los pasa, fijar `paths.origin` en build. Probar login y remote forms desde cada host, no solo localhost.
- **TS7.** No intentar subirlo en esta migración: Kit 3.1.0, svelte-check 4.7.7 y typescript-eslint 8.71.2 no lo soportan. Queda como plan separado cuando cambien los peers.
- **Herramientas auxiliares.** `knip`, `svelte-doctor`, `lilmolly` y `open-codebase-index` pueden no entender `#lib`; correrlos y, si fallan, ajustar configuración sin volver a `$lib`.
